# Daily Paper Reader 增量集成计划

**决策。** 第一批实现桥接候选通道与稳定的原文定位，沿用现有每日推荐、读者状态和发布系统。五维评审先影子运行。跨领域方法论文可以因一个经核验的长板获得阅读席位。现阶段没有证据支持全库换向量、安装第二套文档平台或删除现有推荐引擎。[源码决策矩阵](upstream_integration_review.md) · [CPU 实验与复现](upstream_feasibility_report.md)

## 提议的数据流与接口

1. 从最后成功覆盖的 UTC 日期与本轮排他截止日确定缺失窗口。沿用现有 arXiv/会议源的日期精度和同版本约束。日常兴趣词继续分流到 BM25 和语义 RPC。
2. 从选中方向的研究问题建立 BridgeMap，记录来源兴趣、目标分类、方法词、迁移理由、模型与提示版本。优先使用已保存的映射。映射变化时才重新生成，允许使用预先审核的静态词表。桥接查询在原关键词门槛之前进入单独的有界通道，保留原 ID、类别与各路名次。
3. 既有通道照常运行。桥接通道先用上游匹配器和分类，按日最多送 5 篇有命中的候选到证据核验；相同作品的不同版本沿用宿主去重规则，版本与日期证据保留。任何来源都不能仅凭跨域标签直通发表。
4. 对入围版本优先读 HTML。复用同一棵 DOM 导出全文以及可选证据索引。每条索引记录 paper_id、版本、source_url、源哈希、section/element ID、短引文、定位类型。PDF 路径保存页、坐标、页尺寸与原文；图表另带编号、caption 和提取器版本。字符串或版本校验失败则记录缺失原因。读者原有文本、图片 URL 和 route 继续可用。
5. 在已有批量结构化评审请求里增加五类可空判断，每项附证据、解释和适用条件。输入只用候选的实际片段，正文缺失时保留 abstract-only 来源。资格和呈现分开存储。保留原排序与新提名的并排审计记录，预算内经确认的条目进入现有 feed、目录、站点及 Pages 发布流程。

| 价值维度 | 足以进入人工对照的证据 | 常见误判 |
|---|---|---|
| Idea / Modeling Insight | 推导、模型对应关系、成立条件，例如 SQP 与 iLQR | 把一次改名当成新机制 |
| Experimental Design | 匹配对照、消融、样本选择、可复现实验协议 | 用更高成功率代替对照设计 |
| Engineering Craft | 可定位的实现细节、配置、资源权衡或复现工件 | 仅凭“开源”宣言打高分 |
| Visualization / Presentation | 图表准确表达变量、比较或体系结构，caption 和图号能对应 | 把画面美观或图的数量当作贡献 |
| Empirical Findings | 测量、条件、基线、效应及其不确定性 | 把作者的概括外推到未测场景 |

每项允许“有支持的长板 / 有支持的一般表现或局限 / 证据不足”。探索提名必须写明可借用的机制或结果。一个维度的可靠证据可以触发提名，另一个维度的未知不抵消它；提名后校验引文、研究约束和名额。暂不规定把五维相加、取最大值或使用统一分数阈值。先在相同成本下比较原榜、桥接+证据提名、可选去冗余三组。MMR 只有在足量冗余且盲评有收益时再比较；用同一候选集合和同一最终数量。显式负反馈只调相同研究方向，并单独评估是否误伤少数方法。

**保留、替换、删除。** 保留 SQL、384 维 embedding、来源路由、RRF、远端重排、反馈权限、精读摘要、全文缓存、reader 与 legacy 发布契约。拟替换的是探索通道中重复自写的英文短语匹配需求，以及新提名路径上“所有候选一律通过同一总分硬门”的资格判断。legacy 的无图注批量导出不能直接冒充目标编号预览。当前删除清单为空；只有验证覆盖当前调用者且回退可用，才考虑删除对应 PDF 的手工候选区选择逻辑。无需自行维护整套 PDF 布局模型、跨领域匹配器或向量数据库。

## GitHub-hosted CPU 自动化与持久性

本地检出分支 dev 的实际 cron 是 UTC 18:37（北京时间次日 02:37），run job 要求 dev，schedule 取默认分支。只读 `git ls-remote --symref` 查得 MuX2001 fork 默认分支确为 dev（远端 HEAD `0192449d`），本地旧 origin/HEAD 仍指向 main。不同 fork 必须核对实际默认分支、启用的 Actions 与已有分支根目录 Pages 源。远端提交和本次宿主不同，本次未验证任何具体远端提交的运行结果。[GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

- **调度与补漏。** 保留每日 cron 以及手动补跑入口。每次从持久清单找最早未确认日期，按 UTC 日切片，留可配置重叠以覆盖延迟入库。一个 run 最多补三天，其余排到下个定时任务。只有检索成功且时间边界明确的空日才记 empty。源不可用和未知日期记录 pending。超过源保留期的缺口显示 incomplete，不能自动填零。
- **状态。** 在 fork 已有 `archive/` 中按日期、来源、查询指纹保存小型清单，标记 retrieved/evaluated/staged/published 和对应版本、策略哈希与输出 commit。把公开状态与私人反馈分开。将候选/结果先原子落盘再推进高水位，阶段失败可从已完成输出恢复。需要可重放的已付费结果存受限持久工件或既有允许的持久结果中，Actions/cache 只加速。artifact 的保留期不等同于永久状态。
- **限流与恢复。** 对 429 尊重 Retry-After，对超时与 5xx 设有界指数退避、抖动和每源并发上限；无效结构只在原批预算内修复。缓存键含版本、原文、提示/schema、模型、端点和组合上下文。重放前校验内容哈希、ID 和证据映射。批量评审完成即写检查点；失效后先核对持久清单，达到付费上限停止该通道。保留现有串行发布并在推送前核对目标 SHA，防止旧结果覆盖新目录。
- **发布与观测。** reader-publish 已构建并调用 request_pages_build。成功条件是部署提交对应本轮结果，且线上目标 feed、目录与至少一篇论文可读。发布失败单独重试。沿用 always 上传运行报告，增加每源命中、淘汰原因、证据缺失、缓存命中、每模型 token、429、阶段时长、峰值 RSS、磁盘与最后成功日期；失败工件最小范围，不包含 secret、服务角色 key 或私人反馈内容。
- **运行依赖。** 优先 ubuntu-latest、Python 3.11、远端模型已有配置；本轮短语召回和来源定位本身零模型调用。桥接可用固定词表，独立于 Claude CLI、额外数据库、GPU 和付费解析器。对没有可用模型凭据的 fork，当前 minmax 会报错；实施时应提供显式低成本模式，定时发布已有检索排名、原文摘录和来源，把五维字段标为待评审，后续用原缓存恢复。此模式不声称产生了模型分析。
- **回滚。** 按开关逐项停用桥接、五维或 PDF 提取器，恢复原名单并记录决定；已发布论文、路由和读者状态不变。没有新功能命中的日子必须仍能完成常规发布。

## 每日容量与成本

以 20261127 的 26 篇 shortlist 作容量案例。历史缓存中 narrative 首轮为 46 次响应、357555 tokens，6 篇修复另 6 次、51526 tokens。独立终评 7 次、51045 tokens、累计模型等待 29.18 秒，选中 10 篇。该组合合计 **59 次、406456 输入 + 53670 输出 = 460126 tokens**。另一份 cold/cost.log 对同规模 narrative 记录 28 次、217714 tokens、203.95 秒、1 篇失败；这是不同运行，不应与首轮及修复相加。这些数字均未计检索、远端 embedding/rerank 或前段 Step 4。模型价格用运行当天实际输入/输出单价，示例费用为 `0.406456 × 每百万输入价格 + 0.053670 × 每百万输出价格`，缓存折扣按服务商账单另核。

**用于实施排期的估算。** 26 篇在相似文档上按本机解析时间外推，纯 HTML 约 5–9 秒，全部回退宿主 PDF 提取再加约 3 秒，不含下载、图像编码、网络等待或编译。首次无缓存、20–30 篇按以上同量级历史数据，先给检索/下载与重排 5–15 分钟、分析与修复 5–20 分钟、构建发布 3–10 分钟，合计 **13–45 runner 分钟/日**作为容量假设；现行 330/360 分钟是 step/job 极限。试点给新增部分单 worker、峰值目标 1 GiB、临时盘 1 GiB；现有两样本进程峰值约 139 MiB，17 MiB 输入不能代表重型解析器。实测 p95 超预算则先降并发或减少增强候选。

**增量 API 预算。** 固定映射与纯短语得分为零；映射变更最多一次生成/方向，建议限 2000 输入、1000 输出。每天新增探索证据最多五篇，合一批终评，建议含一次修复上限 2×(8000 输入+1500 输出)；超过则延后。五维输出会变长，必须用实测替换此假设。已有 26 篇终评按 6 个正常批次估计，按批次计入同一上限。总预算还需加各源查询数×分片数、嵌入的新查询数、重排批次数和 Step 4 的真实 token；这些在现有 26 篇终评日志中不可见，需由试点分别计量。完整缓存重放的新增付费调用验收目标为 0。

**上线前的证据。** 在真实 hosted runner 验证无本地模型包冷启动、报告实际 p50/p95 与账单、缓存淘汰、缺一天的定时恢复、429、版本冲突、发布失败后的同 SHA 重试。留下 run URL、artifact 清单、commit 与 Pages 检查记录。本轮本地 CPU 结果支持进入实施和托管试点，尚不足以批准生产替换。
